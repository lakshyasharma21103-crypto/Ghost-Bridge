## Scope and purpose

D2-01R1 Revision 2 is the first bounded remaining D2-01 implementation
contract after the integrated D2-01A and D2-01B workflow sub-slices. Its
purpose is reusable shared canonical wire vocabulary and generic
representation and predicate infrastructure. It does not absorb later
object-family semantics.

### Accepted candidate artifact families

#### A. Neutral raw JSON validation substrate

For protocol inputs whose rules require it, a later authorized implementation
may provide reusable machinery for:

- strict UTF-8;
- BOM rejection where required;
- duplicate raw JSON member detection after escape decoding;
- source-token numeric eligibility;
- negative-zero rejection;
- applicable H-12 raw and structural resource limits; and
- preservation of information that ordinary JSON parsing would otherwise
  lose.

This is generic substrate. It is not the H-12 network receive implementation.

#### B. `CanonicalBase64url32Octets`

A reusable strict representation for exactly 32 octets encoded as canonical,
unpadded base64url.

#### C. `SemanticCommitmentRef`

The already governed closed semantic type is:

```json
{
  "profile": "<exact-approved-H-10-digest-profile>",
  "domain": "<exact-approved-H-10-domain>",
  "value": "<canonical-43-character-unpadded-base64url-digest>"
}
```

The owning schema remains responsible for the exact permitted `profile` and
`domain`. No algorithm, domain, purpose, projection, canonicalization, or
authority may be inferred from digest length, location, member name, or object
shape.

#### D. `Origin` — pure structural and canonical representation only

Reusable representation work may encode the accepted structured origin:

- scheme;
- tagged host union;
- explicit port;
- canonical DNS representation;
- canonical IPv4 representation;
- canonical IPv6 representation;
- IPv4-mapped-IPv6 rejection; and
- structural scheme distinction.

R1 owns only canonical representation. It does not decide whether a particular
origin is permitted for an operation.

#### E. Generic `TimeEvidence` predicates

Reusable semantic predicates may cover lower/upper ordering and interval
non-emptiness. They do not absorb Task, Receipt, retention, deadline,
lifecycle, or state-machine semantics.

#### F. Generic exact artifact-byte integrity verification

Reusable verification may cover the exact byte stream, declared `byteLength`,
and exact SHA-256 checksum representation. It does not decide discovery,
release publication, manifest authority, Trust, release support, or download
behavior.

#### G. `ExtensionIdentity`

Reusable canonical structural and equality validation may cover the already
governed extension identity representation. It does not decide extension
selection, criticality, participation, requiredness, forwarding, object-local
placement, unknown-extension behavior, H-10 coverage, or extension graduation
and evolution. Those remain owned by their accepted semantic authorities and
later object families.

## Binding independent-review corrections

All eight corrections below are binding qualifications on any later authorized
implementation of this contract.

### Correction 1 — Origin and the plain-HTTP boundary

The shared `Origin` representation may structurally represent the literal
scheme `http`. Arbitrary HTTP Origin values must not be treated as
semantic-positive Governed-origin fixtures. Plain HTTP is valid only in the
exact H-12-authorized loopback test/development context, which R1 does not
implement. Structural recognition of `http` therefore must not imply that an
endpoint is semantically usable. Production Governed remote use remains
HTTPS-only under the accepted higher authority.

### Correction 2 — `KeyThumbprintReference` rationale

`KeyThumbprintReference` remains excluded. H-10 key-purpose vocabulary is
already accepted, and R1 is not waiting for key-purpose semantics. The generic
`keyId` lexical and bounded representation and its downstream binding are not
sufficiently fixed for R1. R1 must not invent them.

### Correction 3 — Honest resource-limit boundary

A raw-input validator receiving an already materialized byte buffer cannot
claim that it prevented the network or runtime from allocating that buffer.
R1 tooling may validate an already bounded byte source, must avoid unnecessary
unbounded secondary allocation, and may test the accepted H-12 limits. It must
not claim to enforce the H-12 network receive limit unless a later transport
implementation applies limits while reading. Transport streaming and read
enforcement remains later H-12 implementation work.

### Correction 4 — Byte-exact raw-parser fixtures

Raw-input tests must preserve exact source bytes for malformed UTF-8, BOM,
duplicate raw members, escape-equivalent duplicate members, source-number
spellings, and negative zero. A fixture pipeline must not parse and then
ordinary-JSON-reserialize these cases before validation, because that destroys
the evidence under test. A later implementation should use byte-exact fixture
assets or another explicit lossless byte carrier.

### Correction 5 — Do not duplicate semantic machinery

The repository's current semantic validation already contains predicates for
`TimeEvidence` and artifact-byte integrity. A later implementation must inspect
that machinery; reuse, converge, or intentionally refactor it; avoid parallel
competing definitions; retain one authoritative executable predicate for each
generic semantic concern; and add regression and drift protection. Existing
implementation remains evidence rather than protocol authority, but
unnecessary semantic duplication is prohibited.

### Correction 6 — Production-grade Origin algorithms

DNS/IDNA and IP validation must reproduce the accepted Ghost Bridge acceptance
set. Implementation must not blindly delegate protocol law to generic URL
parsing, implicit platform normalization, an IDNA library with materially
different acceptance behavior, or a loose IPv6 regular expression. IPv6
canonicality should be proven through parse plus canonical re-encoding
semantics, including RFC-5952-style behavior and mapped-address rejection.
Generic URL parsing must not normalize an authority before Ghost Bridge
validation.

### Correction 7 — Generic ownership is not contextual completion

R1 ownership of the generic primitive or predicate for rows 8–13, 16, and 17
does not close a consuming family. Later schema and object-family work must
prove correct binding, placement, authority context, semantic owner, and
failure behavior. Generic R1 completion must not be counted as downstream
family completion.

### Correction 8 — Existing schemas are immutable

Introducing shared primitives later must not silently rewrite frozen schema
contents under an existing immutable `$id` for reuse or presentation. New
artifacts may reference new shared primitives where authorized. Replacement of
an existing immutable asset must follow the applicable versioned
artifact-governance mechanism. There may be no in-place semantic mutation under
an existing identity.

## Production-engineering requirements

A later R1 implementation must support independent, cross-language protocol
engineering rather than act as a JavaScript convenience layer. It must
separate:

1. raw-input and tokenization concerns;
2. structural JSON Schema validation;
3. canonical primitive predicates;
4. the semantic predicate registry; and
5. the fixture and evidence harness.

It must not create a monolithic helper that becomes an implicit protocol
oracle. Required engineering properties are:

- deterministic validation;
- fail-closed behavior;
- bounded resource usage;
- immutable, offline schema resolution;
- no network retrieval during validation;
- explicit errors;
- testable semantic predicates;
- implementation-neutral fixture evidence;
- byte-exact malformed-input cases;
- cross-language reproducibility;
- drift guards between declarations and executable checks; and
- no promotion of runtime or SDK implementation into protocol authority.

MCP and other mature protocol repositories may be consulted only for schema
organization, package or module separation, parser boundaries, failure
handling, fixture architecture, conformance structure, drift guards,
cross-language parity, and release or test hygiene. They must not supply Ghost
Bridge semantics.
