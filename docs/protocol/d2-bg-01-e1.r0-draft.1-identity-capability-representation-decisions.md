## Accepted Decision 1 — IssuerIdentity

`IssuerIdentity` is exactly a 45-character ASCII string matching:

```text
^urn:uuid:[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$
```

The following rules apply:

- exact code-unit equality;
- no normalization;
- no aliases;
- no reuse;
- no reassignment; and
- no authority from possession.

`IssuerIdentity` is semantically distinct from H-11
`ContinuityDomainIdentity`. Trust evidence may bind them, but neither is
derived from or substituted for the other.

## Accepted Decision 2 — AgentIdentity

`AgentIdentity` uses exactly the same canonical lowercase UUIDv4 URN lexical
language and bounds as `IssuerIdentity`, but remains a distinct semantic type.
It is generated once when establishing the logical Agent identity before its
first accepted Passport binding.

The following rules apply:

- exact equality;
- no normalization;
- no aliases;
- no reassignment;
- no reuse; and
- no authority from possession or equality alone.

The same `AgentIdentity` under changed issuer or Passport evidence proves no:

- issuer continuity;
- Passport continuity;
- Trust continuity;
- Connection continuity;
- authorization;
- ownership;
- substitution; or
- migration continuity.

A material evidence change follows the applicable new preview, consent, and
new or replacement Connection path. This decision does not introduce an
Agent-controller authority role.

## Accepted Decision 3 — PassportIdentity

`PassportIdentity` is the closed, extension-free object containing exactly:

```json
{
  "issuer": "<IssuerIdentity>",
  "local": "<PassportLocalIdentifier>"
}
```

`PassportLocalIdentifier` is 1 through 128 ASCII characters matching:

```text
^[a-z0-9](?:[a-z0-9._-]{0,126}[a-z0-9])?$
```

The following rules apply:

- lowercase ASCII only;
- exact code-unit comparison;
- Passport equality is the exact tuple `(issuer, local)`;
- no normalization;
- no aliases;
- no case folding;
- no Unicode equivalence;
- no percent-decoding equivalence;
- no identifier reuse;
- raw duplicate members reject;
- member order is nonsemantic; and
- `local` alone is never `PassportIdentity`.

Any separately carried Passport issuer evidence must exactly equal
`PassportIdentity.issuer`.

## Accepted Decision 4 — PassportVersion

`PassportVersion` is 1 through 64 ASCII characters matching:

```text
^[a-z](?:[a-z0-9._-]{0,62}[a-z0-9])?$
```

The following rules apply:

- exact code-unit equality;
- meaningful only with one complete `PassportIdentity`;
- no normalization;
- no aliases;
- no numeric ordering;
- no lexical ordering;
- no locale ordering;
- no semantic-version interpretation;
- no ranges;
- no latest or greatest selection;
- no nearest selection; and
- no fallback.

For one exact protocol release and `PassportIdentity`, one exact
`PassportVersion` is allocated to one immutable Passport meaning or reference.
It **MUST NOT** later be reused or repointed to different Passport bytes or
semantics.

## Accepted Decision 5 — CapabilityNamespaceIdentity

`CapabilityNamespaceIdentity` uses exactly the same canonical lowercase UUIDv4
URN lexical language and bounds as `IssuerIdentity`, but remains a distinct
semantic type. It is generated once by an independent capability namespace
publisher as a collision-resistant namespace identity.

The following rules apply:

- exact equality;
- no normalization;
- no aliases; and
- no reuse.

`CapabilityNamespaceIdentity` proves none of:

- ownership;
- authenticity;
- Trust;
- eligibility;
- signing authority;
- transfer right;
- recovery right;
- revocation state;
- Connection authority; or
- execution authority.

No new protocol authority role is created. The superseded Revision 2
governance-root, genesis, transfer, recovery, and revocation subsystem is not
accepted by this record.

## Accepted Decision 6 — Capability namespace classes

There are exactly two semantic classes: `core` and `external`.

### Core

- Core is release-owned.
- Allocation requires the exact immutable release registry.
- External parties cannot allocate or claim Core keys.

### External

- External is decentralized.
- Independent namespace generation requires no central Ghost Bridge approval.
- Namespace generation or UUID possession grants no capability legitimacy.

External capability eligibility remains governed only by existing D1 release,
evidence, source, Host, Offer, Grant, consent, policy, Connection, and later
execution-gate semantics.

D2-BG-02 may define exact source and release registry rules. It **MUST NOT** be
interpreted as automatically requiring centralized enumeration of every
external namespace.

## Accepted Decision 7 — CapabilityKey

`CapabilityLocalName` is 1 through 128 ASCII characters matching:

```text
^[a-z0-9](?:[a-z0-9._-]{0,126}[a-z0-9])?$
```

A Core `CapabilityKey` is exactly:

```json
{
  "namespaceClass": "core",
  "name": "<CapabilityLocalName>"
}
```

An External `CapabilityKey` is exactly:

```json
{
  "namespaceClass": "external",
  "namespace": "<CapabilityNamespaceIdentity>",
  "name": "<CapabilityLocalName>"
}
```

The following rules apply:

- objects are closed;
- objects are extension-free;
- all shown members are required;
- `namespace` is forbidden for Core;
- `namespace` is required for External;
- raw duplicate members reject;
- member order is nonsemantic;
- no normalization;
- no aliases;
- no case folding;
- no Unicode equivalence; and
- no percent-decoding equivalence.

Core equality is the exact tuple `("core", name)`. External equality is the
exact tuple `("external", namespace, name)`.

`CapabilityKey` remains semantically distinct from:

- `ExtensionIdentity`;
- `ReleaseRegistryToken`;
- schema identities;
- artifact identities; and
- operational identifier classes.

## Accepted Decision 8 — CapabilityVersion

`CapabilityVersion` is 1 through 64 ASCII characters matching:

```text
^[a-z](?:[a-z0-9._-]{0,62}[a-z0-9])?$
```

The following rules apply:

- exact code-unit equality;
- meaningful only with one complete `CapabilityKey`;
- no normalization;
- no aliases;
- no numeric ordering;
- no lexical ordering;
- no locale ordering;
- no semantic-version interpretation;
- no ranges;
- no latest or greatest selection;
- no nearest selection; and
- no fallback.

Duplicate or conflicting declarations for the same exact `CapabilityKey` plus
`CapabilityVersion` reject. Different exact versions remain distinct exact set
members unless immutable release or contract evidence explicitly establishes a
conflict.

Within one exact protocol release, one exact `CapabilityKey` plus
`CapabilityVersion` pair **MUST** bind one exact immutable
`CapabilityContractReference`. A different contract artifact identity,
integrity reference, or incompatible contract meaning under that same tuple is
a conflicting record and rejects. The pair **MUST NOT** be silently repointed.

## Accepted Decision 9 — Generic immutable artifact identities

Typed immutable artifact identities use exactly the canonical lowercase UUIDv4
URN lexical language defined for `IssuerIdentity`.

The following rules apply:

- the owning typed field supplies the semantic artifact class;
- equal UUID text does not permit cross-class substitution;
- artifact identity is distinct from artifact integrity;
- artifact identity is distinct from provenance;
- artifact identity is distinct from semantic object identity;
- artifact identity grants no authority;
- `ArtifactByteIntegrityRef` remains separate;
- changed artifact bytes require a new immutable artifact identity and new
  corresponding `ArtifactByteIntegrityRef`; and
- a digest does not become semantic artifact identity.

## Accepted Decision 10 — PassportReference

`PassportReference` is a closed object containing exactly:

- `passportIdentity`;
- `passportVersion`;
- `protocolRelease`;
- `passportArtifact`; and
- `artifactByteIntegrity`.

Every member is required. Each uses its exact approved or controlling type.
The complete reference **MUST** resolve exactly one immutable historical
Passport artifact. Mutable latest or current resolution is prohibited.

The referenced Passport still independently must satisfy applicable:

- Agent binding;
- issuer evidence and signature;
- proof;
- release;
- Trust; and
- every other D1 gate.

## Accepted Decision 11 — CapabilityContractReference

`CapabilityContractReference` is a closed object containing exactly:

- `protocolRelease`;
- `capabilityKey`;
- `capabilityVersion`;
- `capabilityContractArtifact`; and
- `artifactByteIntegrity`.

Every member is required. The capability key is complete. The reference is
immutable and historically resolvable.

For one exact protocol release and exact `CapabilityKey` plus
`CapabilityVersion`, conflicting:

- contract artifact identities;
- integrity references;
- immutable contract mappings; or
- incompatible contract semantics

reject rather than merge, replace, rank, select first, or select last. Current
deployment availability is separate narrowing evidence and does not alter
capability or contract identity.

- non-authority of an External namespace UUID;
