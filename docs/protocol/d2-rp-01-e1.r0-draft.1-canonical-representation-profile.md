This record uses three classifications:

1. `INHERITED_D1_TRANSCRIPTION`: accepted H/REQ authority already fixes the

### Tagged Workspace carrier — D2R-010

D1 fixes exactly two semantic classes: Workspace absent, or Workspace present
with one exact validated value. The accepted closed JSON carrier is exactly:

```json
{ "state": "absent" }
```

or:

```json
{ "state": "present", "value": "<validated-workspace-id>" }
```

The absent branch forbids `value`; the present branch requires exactly one

## Accepted D2 representation selections

### JSON Schema dialect and validator contract — D2R-001

Every canonical schema uses this exact dialect identifier:

```text
https://json-schema.org/draft/2020-12/schema
```

The validator contract requires the standard 2020-12 Core, Applicator,
Unevaluated, Validation, Meta-Data, Format-Annotation, and Content
vocabularies. Ghost Bridge does not depend on implementation-specific `format`
assertion. A `format` annotation may document intent but is not the sole
validator for a Ghost Bridge primitive.

Structural schema is not the complete semantic oracle. The applicable raw or
semantic validation layer retains calendar validity, UTF-8 byte length,
duplicate-member rejection, source-token and negative-zero checks, Unicode
eligibility, canonical base64url, route decoding, cross-field equality,
authority, lifecycle, clocks, state transitions, anti-rollback, and atomicity.

Schema validation uses an offline immutable `$id`-to-asset mapping and must not
require network retrieval. Composition behavior must be reproduced by at least
two independent Draft 2020-12 validators before D2-01 exit.

### Schema, bundle, and evidence identities — D2R-002 / D2R-003

Schema and bundle identities are fixed standardized UUID URNs:

```text
urn:uuid:<canonical-lowercase-hyphenated-UUID>
```

Exact UUID values may be generated once during authorized D2 asset creation,
checked for duplicate allocation inside the bundle, recorded in the immutable
manifest, and frozen. Human approval of each randomly allocated UUID is not
required because its bits carry no protocol semantics.

UUIDs are opaque artifact identifiers. They have no release ordering,
compatibility, support, negotiation, security-eligibility, authority, or
lifecycle meaning. The manifest owns each UUID's logical name, exact protocol
release relationship, immutable local path, asset class, and dependencies.

A D2 slice/evidence record may carry an asset revision and a
`foundation-partial` completeness status. Neither is a second protocol version
or a wire compatibility identity. The final bundle must remain the single
release-subordinate bundle identity required by H-03/H-13.

### Semantic commitment reference — D2R-004A / D2R-018

`SemanticCommitmentRef` is a distinct closed semantic type carrying:

```json
{
  "profile": "<exact-approved-H-10-digest-profile>",
  "domain": "<exact-approved-H-10-domain>",
  "value": "<canonical-43-character-unpadded-base64url-digest>"
```

The owning schema supplies the exact permitted profile and domain. No verifier

### Operational resource identifiers — D2R-005

Distinct operational semantic types may share this representation:

- exact decoded length: 16 octets; and
- wire form: strict canonical unpadded base64url, therefore 22 characters.

Applicable types include Connection, Invocation, Task, Result, Receipt,
Approval Challenge, and Approval Decision where their owning schemas assign
that operational class. Each remains a separate schema and semantic type.

This representation does not prescribe an entropy source or generation
algorithm, make possession authoritative, or apply to Agent, Passport,
Organization, Workspace, capability, registry, extension, schema, bundle,
artifact, key, or thumbprint identities. Generation/security policy remains
separately owned.

### Organization and Workspace identifiers — D2R-006

Organization and Workspace use separate case-sensitive opaque ASCII types.
Each value contains 1 through 128 ASCII characters and matches:

```regex
^[A-Za-z0-9](?:[A-Za-z0-9._:-]{0,126}[A-Za-z0-9])?$
```

The exact grammar and bound above are explicitly human-approved under
D2R-006G Option A in D2-RP-01 Revision 3; they are not an implementation
default. D2R-006G is a named sub-selection of D2R-006, not an independent
top-level D2R matrix row.

The exact consequences are:

- the first character is ASCII alphanumeric;
- the last character is ASCII alphanumeric;
- interior characters may additionally use `.`, `_`, `:`, and `-`, and that
  interior punctuation may repeat;
- comparison is case-sensitive exact code-unit equality;
- whitespace, Unicode, slash `/`, backslash `\`, percent-encoded alternate
  spellings, and control characters are prohibited; and
- trimming, case folding, Unicode normalization, aliasing, coercion, and
  truthiness-derived identity are prohibited.

The punctuation `.`, `_`, `:`, and `-` is opaque identifier content only and
must not be interpreted as hierarchy, namespace, path, parent, child, or
authority syntax. The common representation does not make Organization and
Workspace interchangeable, and no representation may convert one type into
the other merely because their underlying strings are equal.

### Participant-owned correlation bytes — D2R-008

Request, message, correlation, trace, and parent/child identifiers preserve the
generating participant's exact bytes:

- decoded length: 1 through 64 octets; and
- wire form: strict canonical unpadded base64url.

Validation decodes exactly once, enforces the decoded bound, re-encodes without
padding, and requires exact textual equality. Internal, peer, and parent values
remain separately labeled. They are bounded non-secret correlation metadata,
not authority, idempotency, an operational object identity, or a global
uniqueness claim.

### Invocation idempotency carrier — D2R-009

REQ-INV-0007 already requires a separate stable Invocation identity and an
idempotency namespace/key. The accepted closed carrier is:

```json
{
  "idempotency": {
    "namespace": "<canonical-base64url>",
    "key": "<canonical-base64url>"
  }
}
```

The namespace is 1 through 64 Host-owned octets. The key is 1 through 128
Host-owned octets. Both use the same strict decode, bound, canonical re-encode,
and equality checks as other canonical base64url byte strings.

The namespace is not a release registry identifier. Correlation, Approval,
Task, transport, or other nearby IDs cannot substitute for the complete
Invocation/idempotency identity.

### Canonical timestamp — D2R-011

The canonical lexical representation is:

```text
YYYY-MM-DDTHH:mm:ss.sssZ
```

Its structural shape is:

```regex
^[0-9]{4}-(0[1-9]|1[0-2])-(0[1-9]|[12][0-9]|3[01])T([01][0-9]|2[0-3]):[0-5][0-9]:[0-5][0-9]\.[0-9]{3}Z$
```

The semantic validator additionally requires the proleptic Gregorian calendar,
year `0001` through `9999`, an existing calendar date, uppercase `T` and `Z`,
UTC only, no numeric offset, exactly three fractional digits, and seconds
`00` through `59`. Leap-second input is rejected.

Comparison uses the represented instant only after canonical parsing. Lexical
ordering of valid canonical values equals instant ordering. Millisecond
precision does not imply event uniqueness; state versions, Trust sequence,
durable serialization, and race rules resolve events sharing a millisecond.

### Exact and interval time evidence — D2R-012

Exact time evidence uses:

```json
{ "kind": "exact", "at": "<canonical-timestamp>" }
```

Interval evidence uses:

```json
{
  "kind": "interval",
  "lower": { "at": "<canonical-timestamp>", "inclusive": true },
  "upper": { "at": "<canonical-timestamp>", "inclusive": false }
}
```

The two `inclusive` values preserve `[L,U]`, `(L,U]`, `[L,U)`, and `(L,U)`
without rounding or collapsing edge meaning. Lower/upper ordering and a
nonempty represented interval remain semantic checks.

### Trust sequence — D2R-015

Trust sequence is a JSON integer with:

- minimum: `1`;
- maximum: `9007199254740991`; and
- genesis: `1`.

Zero, negative, fractional, noncanonical, coerced, clamped, reset, wrapped, or
overflowing values are invalid. Overflow fails and cannot change the continuity
domain or durable floor.

### Authority-bearing path resource encoding — D2R-016

Each authority-bearing resource path segment is:

```text
canonical-unpadded-base64url(exact route-specific identifier bytes)
```

Validation must:

1. reject percent-encoded or alternate transformed spellings;
2. decode exactly once;
3. validate decoded bytes against the route's actual identifier schema;
4. canonically re-encode the same bytes without padding;
5. require exact raw textual equality; and
6. only then resolve the resource.

The route encoding does not require every underlying identifier to contain 16
octets. The inherited 8-KiB raw request-target limit remains in force.

### Structured origin and host — D2R-017

An origin is a closed structured `scheme`, tagged `host`, and explicit `port`.
The host union has `dns`, `ipv4`, and `ipv6` branches.

Example:

```json
{
  "scheme": "https",
  "host": { "kind": "dns", "value": "service.example" },
  "port": 443
}
```

DNS wire values are lowercase ASCII. Internationalized names, when accepted,
use validated IDNA2008 A-label form; raw U-label input rejects, an `xn--` prefix
alone is insufficient, and invalid or non-round-trippable A-labels reject.
Labels contain 1 through 63 octets and a trailing dot is prohibited.

IPv4 uses exactly four decimal octets, each 0 through 255, with no leading zero
except the literal `0`.

IPv6 uses canonical lowercase RFC-5952-style text, without brackets in the
structured value or a zone identifier. IPv4-mapped IPv6 is rejected as an
alternate textual origin representation and must not alias the `ipv4` branch.

Port is always explicit and ranges from 1 through 65535. Production permits
only `https`; `http` is valid only in an exact D1-authorized loopback test or
development context.

H-12 DNS, address, redirect, rebinding, proxy, and NET-B validation remains
semantic validation after canonical parsing. A generic URL parser must not
normalize the authority before Ghost Bridge validation.

### Extension identity — D2R-020

The form remains:

```text
reverse-DNS-owner + "/" + extension-name
```

The owner has at least two labels. Each label contains 1 through 63 lowercase
ASCII letters or digits with internal hyphens only; leading and trailing
hyphens are invalid. The complete owner contains at most 253 characters and
matches:

```regex
^(?:[a-z0-9](?:[a-z0-9-]{0,61}[a-z0-9])?\.)+[a-z0-9](?:[a-z0-9-]{0,61}[a-z0-9])?$
```

The extension name contains 1 through 128 lowercase ASCII letters or digits,
with `.`, `_`, and `-` permitted only internally, and matches:

```regex
^[a-z0-9](?:[a-z0-9._-]{0,126}[a-z0-9])?$
```

Dots in the extension name do not create DNS components and have no separate
63-character subcomponent bound. The complete owner, slash, and extension name
remain subject to the D1-fixed 255-character ceiling.

Optional normally means member absence. Null is valid only when an exact

### D2R-029A — Total JSON Token Counting Algorithm

**Status:** `ACCEPTED`

**Approval date:** 2026-08-20

**Classification:** `D2_REPRESENTATION_SELECTION`

D2R-029A records Option A, the RFC 8259-derived lexical JSON token-counting
model, as the language-neutral executable counting unit for the existing H-12
and D2R-029 ceiling of 16,384 total JSON tokens. The human protocol authority
explicitly approved this exact statement on 2026-08-20:

> I APPROVE D2R-029A OPTION A — RFC 8259-derived lexical JSON token counting.
> For the Ghost Bridge 16,384-token JSON limit, count each of the six JSON
> structural characters `{`, `}`, `[`, `]`, `:`, and `,` as one token; each
> complete JSON string lexeme, including an object member name, as one token;
> each complete JSON number lexeme as one token; and each complete `true`,
> `false`, or `null` literal as one token. Insignificant JSON whitespace and EOF
> count zero. Characters and escape sequences inside a string and characters
> inside a number or literal do not count separately. Counting operates on the
> original strict-UTF-8 JSON source during lossless tokenization before lossy
> object parsing. Exactly 16,384 recognized tokens is within the limit;
> recognition of token 16,385 requires fail-closed rejection and need not consume
> the remainder of the document. This definition changes no existing H-12
> numeric limit or other Ghost Bridge validation rule.

For this limit, one token is counted for each:

- `{`, `}`, `[`, `]`, `:`, or `,` structural character;
- complete JSON string lexeme, including one token for each object member-name
  string lexeme;
- complete JSON number lexeme;
- complete `true` literal;
- complete `false` literal; and
- complete `null` literal.

Insignificant JSON whitespace and EOF count zero. Individual characters and
escape sequences within a string, digits or punctuation within one complete
number lexeme, and individual characters within `true`, `false`, or `null` do
not count separately.

Counting is performed against the original strict-UTF-8 JSON source during
lossless tokenization and before lossy object materialization or parsing. A
count of 16,384 recognized tokens is within this limit. Recognition of token
16,385 requires fail-closed rejection for this limit; an implementation need
not consume the remainder of the document merely to compute a larger count.
All other validation rules continue to apply independently. A source below
this token limit can be invalid for another reason, and malformed source does
not become valid merely because malformed characters did not form a complete
scalar token.

The following examples apply:

| JSON source | Token count |
| --- | ---: |
| `null` | 1 |
| `{}` | 2 |
| `[]` | 2 |
| `[1]` | 3 |
| `{"a":1}` | 5 |
| `[1,2]` | 5 |
| `{"a":[]}` | 6 |
| `{"a":true,"b":null}` | 9 |

For `{"a":true,"b":null}`, the count is `{` 1, `"a"` 2, `:` 3, `true` 4,
`,` 5, `"b"` 6, `:` 7, `null` 8, and `}` 9. Whitespace-only differences do
not change the count. The complete string lexeme `"\u0061"` is one token;
this does not change the separate rule that duplicate member names are judged
after escape decoding. A complete number lexeme is one token; this does not
change H-10 source-number eligibility or negative-zero rules.

This clarification exists so independent implementations agree at the exact
resource boundary without relying on Node.js, JavaScript, Ajv, a particular
parser library, or a parser-event API. Parser libraries differ in whether they
expose punctuation or elide separators, so their token APIs are not protocol
authority. The Ghost Bridge counting rule is language-neutral, applies before
lossy object parsing, and permits bounded hostile-input handling by early
fail-closed rejection when token 16,385 is recognized.

### Artifact byte integrity — D2R-004B

`ArtifactByteIntegrityRef` is a distinct closed type:

```json
{
  "algorithm": "sha-256",
  "value": "<canonical-43-character-unpadded-base64url>",

```

`value` is SHA-256 over the exact artifact byte stream. `byteLength` is the
exact artifact octet length and uses the inherited H-10 safe-integer rules.
Artifact bytes are not parsed, normalized, canonicalized, or converted through
an H-10 semantic projection before this checksum is computed.

Artifact byte integrity is not an H-10 semantic commitment. Conversely, an
H-10 semantic commitment is not a file checksum. Supply-chain signatures,
release signing, publication, and provenance remain H-14/later work.

## Accepted authentication security selection — D2R-027

The accepted custom production baseline is:

| Parameter                   |               Accepted value |
| --------------------------- | ---------------------------: |
| Profile                     | `gb.auth.signed-request-pop` |
| Revision                    |                            1 |
| Credential maximum validity |                     24 hours |
| Request-proof lifetime      |                   60 seconds |
| Request-proof maximum age   |                   60 seconds |

The following are not applicable and are not registered for this baseline
profile:

- reusable authenticated session/channel lifetime;
- reusable authenticated session/channel freshness;
- provider/cache freshness as request-authentication authority; and
- periodic session-style reauthentication/recovery interval.

Twenty-four hours is a maximum, not guaranteed authority duration. Current
revocation, compromise, key ineligibility, Trust failure, Connection expiry or
lifecycle state, authorization, policy, and other D1 gates may terminate
eligibility earlier. Expiry is exclusive, with no grace period.

Cached success, provider defaults, and TLS/channel lifetime cannot extend
authentication validity. Request-proof freshness is distinct from H-11 Trust
freshness. No authentication-profile fallback, bearer-for-PoP substitution,
adjacent-profile trial, or fixture-`none` fallback is permitted.

Credential renewal must preserve the accepted invariant identity/profile
binding where D1 permits same-invariant recovery. A material identity, profile,
issuer, principal, Agent, Passport, audience, tenant, limitation, consent, or
authority change uses the existing D1 replacement path rather than an in-place
authentication mutation.

The accepted tradeoff is explicit: shorter credential/proof bounds would
further reduce credential-theft and replay exposure but increase rotation,
clock, and availability pressure; longer bounds would reduce operational
pressure but increase compromise and captured-proof exposure. This profile
selects a 24-hour credential maximum and a 60-second per-request proof window
for `ghostbridge/e1.r0-draft.1`.

A post-publication change to these values requires a new authentication profile
revision and the applicable new release/bundle treatment.
