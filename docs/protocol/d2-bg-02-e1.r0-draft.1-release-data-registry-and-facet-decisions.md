## Accepted Decision 1 — SER-B-R6 closed registry architecture

Each exact `ProtocolRelease` manifest contains exactly one subordinate artifact
for each of these seven class discriminators:

1. `gb.registry.source-claim-authority`
2. `gb.registry.directional-binding`

5. `gb.registry.external-capability-eligibility`
6. `gb.registry.global-feature-allocation`
7. `gb.registry.authentication-profile`

The following closure rules apply:

- The seven discriminators form a closed class set.
- All seven artifacts load and validate atomically. A partial load has no
  release-data authority.
- A missing, unknown, duplicate, mismatched, or multiply referenced class
  fails the release registry.
- Each subordinate artifact binds to one exact `ProtocolRelease`.
- A class discriminator is not an independent compatibility, negotiation,
  fallback, or release-selection axis.
- The absence of an independent discriminator revision is this accepted
  D2-BG-02 human release-data decision; it is not attributed to D2R-007.
- Facet and authentication-profile entries retain their expressly accepted
  revisions.
- Each artifact has a distinct typed immutable artifact identity and an
  `ArtifactByteIntegrityRef`.
- Artifact identity, class, release, integrity, and manifest bindings are
  immutable and mutually consistent.

## Accepted Decision 3 — corrected SRC-A-R6 source-claim authority

The source-claim classification is atomic by semantic dimension.

- `R` means a required claim when the source instance and dimension are
  applicable.
- `P` means a permitted optional claim; absence means no claim.
- An unlisted source is unauthorized for that dimension and has no claim
  authority.
- A reference or equality binding is governed by DIR-R6 and is not ownership.
- Optional absence is never denial, a default, a wildcard, inheritance, or
  coercion.

The final selected release is not a source claim. Client and Agent derive it
deterministically from validated H-03 participant metadata, current release
evidence, applicable bounds, consent, policy/status/security predicates,
compatibility evidence, and H-04 eligibility. No second release-selection
channel exists.

| Binding | Kind | Required meaning |
| --- | --- | --- |

| Passport issuer → Passport | Source-intrinsic | Issuer identity/evidence binds the exact Passport and version |
| Discovery → Agent/Origin/release record | Source-intrinsic | Current advertisement binds its exact target, Origin, release, and immutable artifact references |
| Grant issuer → Grant | Source-intrinsic | The authenticated issuer binds the exact Grant identity and immutable issuance bounds |
| Grant → Agent/Passport/purpose/organization scope/tagged Workspace scope | Source-intrinsic | Grant scope is immutable and exactly equals the applicable independently authoritative values; tagged Workspace absence is not a wildcard |
| Offer → transaction subset/restrictions | Source-intrinsic | Offer claims bind the exact transaction object without implying a separate issuer identity |
| Host participant metadata → Host identity/release metadata | Source-intrinsic | The Host's participant claims belong to that exact participant |
| Authentication evidence → authentication result | Evaluation comparison | Evidence is verified under the exact selected profile, audience, purpose, principal, and time bounds |
| Trust evidence references → Trust result inputs | Evaluation comparison | References identify evidence; only bounded verification produces Trust validity |
| Passport/Discovery/Offer/Grant/Host/consent/policy claims → candidate | Evaluation comparison | Only same-dimension claims intersect; no source widens another |
| Host exact authentication selection → derived eligible set | Evaluation comparison | Selection must be exactly one member and does not author the set |
| Target identity → Origin | Evaluation comparison | Required target/Origin relationships are verified without treating either as the other |
| Organization → Workspace | Evaluation comparison | Workspace is checked within the exact Organization relationship but remains a distinct identity |
| Profile → facet | Evaluation comparison | Applicable registry relationships are checked; equality or substitution is forbidden |
| Capability key → version → contract reference | Evaluation comparison | All three match their immutable evidence independently |
| Extension → dependencies | Evaluation comparison | Exact finite dependency closure resolves without experiment substitution |
| Validated inputs → selected release | Downstream-result binding | Client and Agent perform H-03 and H-04 deterministic selection to produce one result |
| Selected release → negotiated result | Downstream-result binding | The result records exact facets, profiles, capabilities, restrictions, extensions, experiments, omissions, and evidence |
| Negotiated result + authentication result + consent + Grant/Offer bounds → redemption intent | Downstream-result binding | Field, value, and presence equality is complete before transaction entry |
| Redemption intent → Connection | Downstream-result binding | Only the atomic H-06 commit creates and binds Connection authority |

The following semantic distinctions are invariant:

- `AgentIdentity` is not `PassportIdentity`.
- Passport issuer is not Grant issuer.
- Organization is not Workspace.
- target is not Origin.
- profile is not facet.
- capability key is not capability version and neither is contract reference.
- extension is not experiment.
- Trust evidence reference is not Trust result.
- binding is not claim authority.

No object may bind to a value that exists only after issuance of that object.
A Grant cannot contain a future authentication result, final consent,
negotiated result, redemption intent, or Connection. No future or circular
Connection binding is permitted.

The final dependency is:

`validated inputs → deterministic negotiated result → complete redemption intent → atomic Connection commit`

Only the accepted atomic commit creates Connection authority.

## Accepted Decision 5 — Offer, Grant, and issuer boundary

Accepted REQ-INST authority establishes an exact Grant issuer and requires
authenticated, authorized Grant issuance; the redemption intent retains that
issuer. No accepted H/REQ establishes a distinct Offer-issuer semantic identity,
issuer evidence class, or authority boundary.

Therefore:

- Grant issuer remains an atomic source claim and directional binding.
- Offer remains a transaction-specific subset/restriction source where D1
  assigns it.
- Offer-issuer identity or evidence is absent from SRC-A-R6 and DIR-R6.
- A future Offer-issuer class requires separate accepted human authority.

## Accepted Decision 7 — EXT-B external capabilities

External capabilities obey all of the following:

1. Each external capability contract is independently published and immutably
   identified outside the Core allocation.
2. Passport/manifest authority supplies the maximum eligible capability key,
   exact version, immutable contract reference, and assigned ceiling or
   restrictions.
3. Discovery advertises only the currently deployed subset.
4. Offer and Grant narrow only to transaction-specific subsets/restrictions.
5. Host metadata distinguishes required capabilities from optional interests
   and preferences.
6. Consent supplies an immutable permitted subset.
7. Policy may deny or narrow only.
8. Capability key, capability version, and contract reference agree exactly.
9. Conflicting key/version/contract mappings are rejected. Namespace
   similarity, latest-version lookup, aliases, or defaults cannot resolve them.
10. A namespace prevents collisions only. It grants no identity, ownership,
    authenticity, Trust, publication, compatibility, or execution authority.
11. Historical Connections resolve the exact immutable contract evidence
    committed at establishment.
12. Mutable `current`, `latest`, package, SDK, network, or deployment lookup
    cannot replace or rewrite historical capability meaning.
13. An isolated optional capability conflict may exclude only that exact
    key/version and only when every REQ-VERS-0013 condition permits it.
    Shared-security or Host-required conflicts fail the candidate.

## Accepted Decision 8 — invariant facet-property semantics

The five accepted facets are:

- `gb.facet.host.core`, revision 1 (`HC`);
- `gb.facet.agent.core`, revision 1 (`AC`);
- `gb.facet.trust-verification.core`, revision 1 (`TC`);
- `gb.facet.host.governed-execution`, revision 1 (`HG`); and
- `gb.facet.agent.governed-execution`, revision 1 (`AG`).

Every property in this section has property revision 1 and classification
`invariant`. The English token alone is not its definition; the normative
meaning, role applicability, and failure behavior in each record control.

Failure codes used below are complete semantic abbreviations:

- `FI`: a missing, false, unknown, or contradicted invariant makes the
  applicable facet false and candidate incompatible, without fallback.
- `FA`: deny the operation before authority, state, or effect creation;
  quarantine or recover ambiguous partial state fail-closed.
- `FH`: preserve immutable committed history and reject rollback, mutation, or
  mutable reinterpretation.
- `FP`: emit only the applicable disclosure-safe H-12 outcome.
- `FN`: narrowing may affect only the exact capability/version and may never
  widen or waive a shared invariant.
