# Normative specification gap analysis

## Audit determination

At commit `e2f7aa8bbca278d4e4c0836be33f6f98380eb75e`, Ghost Bridge is **not independently implementable as a production protocol** without reading the official JavaScript implementation and, for the production Host path, Platform code.

The repository contains valuable draft prose, JSON Schemas, TypeScript declarations, runtime validators, security utilities, tests, examples, and Platform controls. They do not form one complete, non-contradictory normative source. Passing tests demonstrate implementation behavior; they do not prove specification completeness.

The local inspection covered `protocol/` documentation, schemas, examples, GBEPs, and threat material; protocol-core, Native Client, Native Agent, Trust, and conformance package sources and public declarations; Platform Native Client integration; relevant unit/integration/security tests; raw and packaged verification scripts; Phase 15C reports and residual inventories; package manifests; and Phase 15C CI workflows. Evidence citations describe repository state, not normative authority.

Evidence path shorthand in the matrix and conclusions is deterministic: a bare specification name such as `tasks.md` means `protocol/specification/0.1-draft/tasks.md`; a bare `*.schema.json` name means `protocol/schemas/0.1-draft/<name>`; `GBEP-*.md` means the same file under `gbeps/`; and `security15c1a.test.js` means `packages/ghostbridge-native-agent/test/security15c1a.test.js`. A leading `:<lines>` continues the immediately preceding full file path.

Independence classifications mean:

- **YES — completely specified:** prose and wire material are sufficient without official source.
- **PARTIAL — some normative or wire details are missing.**
- **NO — implementation source is currently required.**
- **CONTRADICTORY — documents, schemas, declarations, tests, or implementations disagree.**

This audit found no area that qualifies as completely specified for a production 1.0 implementation.

## Contradictions found

1. **Task terminal state:** the client treats `rejected` as terminal (`packages/ghostbridge-native-client/src/index.js:1388-1390`), but `task.schema.json:19`, `tasks.md:3-5`, and `TASK_TRANSITIONS` (`packages/ghostbridge-protocol-core/src/index.js:1291-1304`) omit it.
2. **Install Grant retry/concurrency:** prose says redemption is idempotent and concurrent redemption creates one Connection (`install-grant.md:8-11`). Development-mode code returns the existing Connection (`packages/ghostbridge-native-agent/src/index.js:1551-1564`), while production redemption converts `INSTALL_GRANT_ALREADY_REDEEMED` into an error (`:1793-1807`) and the test explicitly expects a concurrent loser (`security15c1a.test.js`, test beginning at line 1694).
3. **Anti-rollback persistence:** issuer/revocation prose says the highest sequence is persisted (`issuer-discovery.md:11`; `revocation-set.md:9`), but the Native Client default is an in-memory `AntiRollbackStore` (`packages/ghostbridge-native-client/src/index.js:160-164`; implementation at `packages/ghostbridge-trust/src/index.js:1304-1335`). Only the Platform adds durable continuity.
4. **Version choice:** `negotiateVersion` ranks the highest compatible version (`packages/ghostbridge-protocol-core/src/index.js:243-248`), while `checkCompatibility` returns the first common version in input order (`:493-565`).
5. **Passport validation:** `passport.schema.json:7` requires data, delegation, and approval declarations, while runtime `validatePassport` omits those requirements (`packages/ghostbridge-protocol-core/src/index.js:820-840`).
6. **Receipt declarations:** the schema and production runtime use Connection, Passport ID, key, issuer, audience, and trust fields; `ExecutionReceipt` in `packages/ghostbridge-protocol-core/src/index.d.ts:306-340` omits several of them.
7. **Extension bounds:** `extension.schema.json:24-34` permits at most three profiles; runtime validation permits up to ten (`packages/ghostbridge-protocol-core/src/index.js:378-383`).
8. **Size negotiation:** discovery can advertise up to 16 MiB (`discovery.schema.json:26`), but the Native Client constructor clamps its response limit to the 256 KiB core default (`packages/ghostbridge-native-client/src/index.js:144-150`).
9. **Error/status mapping:** Native Agent maps `CONNECTION_NOT_ACTIVE` to 403 (`packages/ghostbridge-native-agent/src/index.js:2967`); Platform maps it to 409 (`backend/src/services/platformNativeClient.service.js:69-70`).
10. **Authentication documentation:** `docs/security/authentication-profiles.md:5` says every profile defines discovery, interaction, storage, audience, refresh/revocation, proof, and errors, but no such normative profile definitions or schemas exist.

## Required conclusions

### 1. Behavior currently only in JavaScript

- Exact version selection/downgrade algorithm and compatibility reason ordering: `packages/ghostbridge-protocol-core/src/index.js:215-255,476-594`.
- Authentication-mode first-match selection and safe binding callback: core `:453-474`; Native Client `:635-692,1443-1472`.
- Preview projection/cache invalidation key: core `:596-655`; Native Client `:612-619,1475-1490`.
- HTTP resources, methods, headers, content-type checks, error statuses, query templates, and body wrappers: Native Client `:1000-1075`; Native Agent `:2720-2970`.
- Idempotency namespace/fingerprint/result replay and retry classifier: Native Agent `:706-723`; Native Client `:1126-1145`.
- Exact approval-action field set, canonicalization, digest, nested-limit comparison, and one-time consumption: core `:1196-1289,1510-1520`; Agent `:732-839,1460-1470,2171-2192`.
- Task transition adjacency, polling backoff/attempt caps, cancellation races, and terminal Task/Receipt transaction: core `:1291-1338`; Client `:834-875`; Agent `:931-1080,1387-1458`.
- Receipt construction/binding and historical verification algorithm: Agent `:2294-2401`; Trust `:1624-1689`.
- Canonical JSON, digest encoding, JWS protected headers/signing input, replay key, and anti-rollback algorithm: `packages/ghostbridge-trust/src/index.js:611-1015,1259-1335,1531-1698`.
- Production authorization evidence, sealed scope bindings, persistent Trust continuity, and Platform error translation: `backend/src/services/platformNativeClient.service.js`.

### 2. Behavior currently only in JSON Schema

- Closed-world `additionalProperties:false`, exact required fields, regexes, lengths, property counts, array bounds, and many enum values across `protocol/schemas/0.1-draft`.
- Passport schema requirements for `dataDeclarations`, `delegationDeclarations`, and `approvalDeclarations` (`passport.schema.json:7`) are absent from the runtime validator.
- Exact `profileSupport`, extension namespace, approval digest, proof, key-purpose, revocation subject, and transport-discovery structural bounds are generally not enumerated in prose.
- Several schemas contain wire fields not represented by public declarations or runtime validators, including Trust Receipt fields and detailed Connection Offer fields.

Schema-only constraints are structural, not a substitute for trigger conditions, lifecycle, authority, or cryptographic byte definitions.

### 3. Behavior currently only in tests or verification fixtures

- Conformance transcript fields, safe-evidence 2,000-byte cap, and redaction regex are defined by `scripts/verifyGhostBridgeBlackBoxConformance.mjs:66-113`, not a conformance specification/schema.
- Negative raw endpoints such as malformed discovery, cross-origin discovery, wrong media type, and oversized response exist only in `scripts/black-box/raw-agent.mjs:360-383`.
- Minimum profile test-count thresholds are verification-script policy in `scripts/verifyPhase15c1a.mjs:80-96`, not normative PASS criteria.
- Twenty-one malicious Install Grant transaction mutations, exact concurrency expectations, restart persistence, and cancellation race expectations are encoded in `packages/ghostbridge-native-agent/test/security15c1a.test.js`, not portable fixtures.
- Platform cross-request continuity and sealed-binding substitution expectations are encoded in `backend/src/tests/platformNativeClient.test.js`, not protocol-wide requirements.

These tests often validate real implementation behavior, but their fixture format and expected result are not independently consumable.

### 4. Behavior currently only in Platform code

- Mapping authenticated Host principals to authoritative organization/workspace/user scope: `authenticatedScope` in `backend/src/services/platformNativeClient.service.js:102-169`.
- Operation-to-permission mapping and exact production authorization evidence: `:28-38,202-280,1012-1133`.
- Durable cross-request Trust continuity beyond the SDK's in-memory store: `PlatformTrustContinuityStore` at `:282-367`.
- Mongo-backed Approval replay consumption and sealed HMAC bindings for Connection/Task/Approval continuation: `:390-419` and `PlatformNativeClientAdapter`.
- Platform-specific error translation and safe product responses: `ERROR_CONTRACT` at `:56-88`.

These may be valid stricter Platform policies. They are not protocol requirements unless Phase 15D.1 deliberately standardizes a minimum.

### 5. Documentation, schema, type, and runtime disagreement

The ten contradictions above are confirmed. The most consequential are Task terminality, production Install Grant retry behavior, anti-rollback persistence, version selection, Passport required fields, Receipt binding fields, and HTTP status mapping.

### 6. Implicit state transitions

- Discovery/verification/preview/authentication/install/Connection lifecycle.
- Install Grant `active → redeemed/expired/revoked` and concurrent redemption outcome.
- Connection `offered → active → revoked`; suspension, expiry, close, replacement, and reauthentication are missing.
- Approval `pending → approved/rejected → consumed`; other Decision values are collapsed by Agent code.
- Full Task transition adjacency is JavaScript-only.
- Receipt availability and historical trust-status changes.
- Issuer review and key lifecycle transition tables are JavaScript-only.
- Revocation cache freshness and anti-rollback checkpoint advancement.

### 7. Errors lacking normative trigger conditions

Nearly every code in `ERROR_CODES` and `TRUST_ERROR_CODES` lacks a complete normative trigger and precedence rule. Priority examples are `NO_COMMON_PROTOCOL_VERSION`, `CONNECTION_NOT_ACTIVE`, `IDEMPOTENCY_CONFLICT`, `APPROVAL_INVALID`, `TERMINAL_PERSISTENCE_REQUIRED`, `PROOF_INVALID`, `REVOCATION_STATUS_STALE`, `REVOCATION_ROLLBACK`, `CONNECTION_TRUST_INVALID`, and `HISTORICAL_TRUST_INDETERMINATE`.

### 8. Cryptographic inputs lacking canonical byte-level definitions

- Approval action and payload digests.
- Capability Contract and Capability Manifest digests.
- Install resolution and Connection Offer digests.
- Request content digest and request fingerprint.
- Receipt output/evidence digests.
- Revocation previous-set digest.
- JWK thumbprints.
- JWS protected header/payload bytes at cross-runtime edge cases.

`proof-profile.md` is directionally useful and Trust JavaScript is concrete, but normative byte algorithms and static vectors are missing. Protocol-core and Trust digest formats also differ.

### 9. Undefined compatibility rules

- Version preference/order, N/N-1, draft-to-stable, downgrade exceptions, and selected-version persistence.
- Feature/profile/per-capability precedence.
- Unknown fields/enums/messages and closed-schema evolution.
- Extension version ranges and removal.
- Stored Connections, Tasks, Approvals, Receipts, Trust checkpoints, and revocation sets across upgrades.
- SDK/package version coupling to protocol/schema versions.
- Security-fix compatibility exceptions, deprecation windows, and EOL.

### 10. Tests improperly dependent on official implementation internals

- `@ghostbridge/conformance` imports the official Native Client, protocol-core validators, and Trust validators (`packages/ghostbridge-conformance/src/index.js:3-18`).
- The “black-box” script imports official version negotiation, validators, Native Client, Trust verification, replay, and anti-rollback helpers (`scripts/verifyGhostBridgeBlackBoxConformance.mjs:9-38`).
- Raw fixtures use the official issuer/Trust toolkit. Process separation prevents direct Agent memory access, but the official TypeScript implementation remains the expectation oracle.

### 11. Blockers for an independent Go or Python implementation

The blockers are the absence of normative lifecycle and HTTP operation contracts; incomplete request/response schemas; undocumented authentication/authorization; implicit Connection/Approval/Task state machines; JavaScript-only approval, idempotency, retry, and Receipt binding rules; two digest systems; no static crypto vectors; undefined compatibility; and a conformance harness that imports official implementation helpers.

### 12. Work required before claiming Ghost Bridge 1.0

Complete Phase 15D.1 and 15D.2; resolve every contradiction; publish a coherent normative specification and canonical schema bundle; provide deterministic golden/malicious/cryptographic fixtures; run implementation-neutral black-box conformance; separate and release supported TypeScript SDK artifacts in Phase 15E; complete a second independent implementation; demonstrate bidirectional interoperability and mixed-version compatibility; complete external security review/remediation; and adopt protocol release, support, deprecation, and graduation policies.
